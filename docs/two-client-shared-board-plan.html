Implementation Plan · Multiplayer

One board, two clients, placing units live.

Turning the local placement demo into a shared, server-authoritative board — where each player watches the other deploy in real time, color-coded by owner.

Server v1 game-server your units opponent authority Board 32 × 48

The short version

This is almost entirely a client-side change. The server already runs an authoritative multiplayer board and broadcasts every placement to the whole room. The one missing half is that the Unity client places units locally and never talks to the network.

Why it's mostly done already

The server is ready; the client is disconnected.

Two sockets in the same room already share one validated board. What's missing is the wire between the click and the server, and rendering what the server reports back.

✓ Server

Each socket gets a unique owner id. Placements are validated (footprint, bounds, overlap) and every valid move broadcasts fresh state to the room. No changes needed.

✓ Network client

GameServerClient.cs already sends placeUnit and receives state — but it isn't in the scene and nothing references it.

× Board manager

BoardManager.cs is 100% local: a click spawns a model on the spot. It never asks the server and never renders remote units.

Target architecture

The board becomes a view of server state.

A click no longer spawns anything directly. It asks the server, the server validates and broadcasts, and every client — including the one who clicked — rebuilds its units from that broadcast.

Three things to reconcile

  • Board size. The client hardcodes 32×32; the server's catalog board is 32×48. Build the grid from server dimensions so no placement lands on a tile that doesn't exist.
  • Ownership. The client always places as "Player 1." In the shared model, your units are whatever the server tags with your id; everything else is the opponent's. Color follows from that.
  • Coordinates. Protocol row = world-X (wide), col = world-Z (deep). Keep tile mapping consistent with the server so a unit lands where it was clicked on both screens.

Editor wiring · your checklist

The click-only steps.

All C# is written for you. These are the Unity Editor actions that can't be scripted:

  1. Open Assets/Scenes/SampleScene.unity.
  2. Create an empty GameObject Net → Add Component → GameServerClient.
  3. Set serverUrl = ws://localhost:7777/ws, roomId = lobby, and a distinct playerName per instance.
  4. Select _BoardManager and drag Net into its new Client slot.
  5. Assign the two owner colors — Mine and Theirs — on _BoardManager.
  6. Run two clients on the same room and place units.

Running two clients

Start the server first, then run two instances against the same room. Simplest is the Editor plus one standalone build; Multiplayer Play Mode (already in the project) is the zero-build option.

# start the authoritative server
cd apps/game-server && bun run dev  # ws://localhost:7777/ws

Done when

What "working" looks like.

✓ Shared view

Two clients join lobby and see the exact same set of units.

✓ Live placement

A places a Footman → within a frame, B sees it appear, opponent-colored. And the reverse.

✓ Rejections hold

An occupied or out-of-bounds placement appears on neither client; the placer gets feedback.

✓ Clean disconnect

When one client leaves, its units disappear from the other's board.

Scope, deliberately

This uses the v1 protocol: no commanders, economy, or battles, and placement is open anywhere on the board — no half-restriction. That's the fastest path to "two clients, one board," and exactly the feature requested. The full match loop (hidden planning, commander pick, simulated battles) already exists server-side and is a separate, larger effort to wire into the client.
